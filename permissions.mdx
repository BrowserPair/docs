## Hard scope

An AI connection selects the browser it can use. Each task has website intent and immutable confirmations. Task authority is evaluated with the account's current Permissions policy; page content and Skills never add authority.

## Account-wide Permissions

The **Permissions** page in the BrowserPair App controls the Standard and Developer modes for every connected AI app, API key, task, schedule and Chrome side panel.

Both modes permit the same tools and websites. They differ in which of the nine sensitive steps prompt you first: payment, sign-in/account security, deletion, sending/publishing, files, passwords/secrets, new websites, form submits and website instructions.

**Standard** asks before sensitive steps by default. **Developer** starts with all nine ask-before switches off, but any switch can be turned back on. Switching to Developer requires an explicit acknowledgement. These modes are account-wide; there is no longer a per-agent Developer timer, consent-screen preset, per-app site editor or per-key capability preset.

Current Chrome website access, managed browser site blocks, user-entered credentials and file chooser, task-required immutable confirmations, ownership/fencing and uncertain-effect recovery remain enforced in both modes.

## Runtime website expansion



A task can start with one or many explicit domains.

When the next destination is outside the current effective task scope, BrowserPair does not navigate silently.

## The approval card

Approvals appear as a BrowserPair card on the task's own tab, or in the BrowserPair side panel when the task has no page yet (click the BrowserPair icon in Chrome's toolbar). The card names the action and its target, for example `Click "Delete repository"`, plus the site and risk; the target text comes from the page and is shown quoted. On high-risk cards Enter rejects, so approving takes a deliberate click (or Tab, then Enter). Using the card never closes the page's own menus or popovers, so an approved click inside an open menu still lands.

Approval emails and system notifications never quote page text; they use BrowserPair's own wording with the site and risk only.

## Developer mode

For fewer questions about sensitive steps, choose the account-wide [Developer mode](/developer-mode) on the Permissions page. It affects every connected agent and keeps immutable browser/task safety checks.

## Organization policy

On managed Chrome, an administrator can set `blockedUrlPatterns` for the BrowserPair extension (host patterns that include subdomains). Blocked sites are refused before any input (`blocked_by_browser_policy`) for navigation, links, forms, frames, redirects and tab adoption. The policy can only remove access; no approval, key or preset can lift it.

## When a capability is missing

A `capability_denied` rejection names the capability the action needs (`requiredCapability`), why (`label_risk` for words such as Send, Delete or Pay on the target, `form_submit`, `key_or_modifier`, `action_kind`) and what the task already has (`grantedCapabilities`). The task must still follow current account Permissions and immutable contract requirements; nothing is granted by page content.

## Removing a browser

Removing a browser revokes its device credential at once and stops its active tasks. Agent keys scoped **only** to that browser are revoked too, so they can never drift to another browser; keys that also cover other browsers keep working for those. The App lists the affected keys before you confirm, and revocation cannot be undone.

## Sensitive-data grants

Protected values are redacted by default. User grants can be scoped to:

- one exact pending action;
- the current task; or
- one agent key until revoked.

Optional domain binding can narrow a grant further.

## High-risk effects

Publish, send, delete, payment, password-related, transfer, and other elevated actions require the corresponding capability plus every confirmation required by policy or the task contract.

<Note>
  **Allow all tools in scope** can remove optional prompts, but it cannot remove a confirmation explicitly required by the immutable task contract.
</Note>
