Every BrowserPair AI connection follows the same account-wide Permissions policy. BrowserPair also enforces the current browser, task requirements, Chrome site access and safe effect recovery. A website, model or Skill never expands authority.

## Account-wide Permissions

Open **BrowserPair App → Manage → Permissions**. Both modes use the same browser tools and websites. Nine switches determine when you are asked about payments; sign-in/account security; deletion; sending/publishing; files; passwords/secrets; new websites; form submits; and website instructions.

- **Standard:** asks before seven sensitive categories; **new websites and form submits do not ask by default**. You may enable those questions.
- **Developer:** starts with all nine questions off; entering the mode requires an explicit warning acknowledgement.
- Your choices apply to connected AI apps, agent keys, Chat, schedules and tasks already running at their next decision.

The previous per-app website editors, per-key permission presets, per-agent Developer timers and reusable agent-specific sensitive grants have been removed from the current interface.

## Unchanged safety boundaries

Chrome website access, managed-browser policy, user-entered credentials and file selection, immutable task confirmations, target rechecks, ownership/fencing and no-replay recovery remain enforced in both modes.

## Runtime website expansion



A task can start with one or many explicit domains.

When the next destination is outside the current effective task scope, BrowserPair does not navigate silently.

## The approval card

Approvals appear as a BrowserPair card on the task's own tab, or in the BrowserPair side panel when the task has no page yet (click the BrowserPair icon in Chrome's toolbar). The card names the action and its target, for example `Click "Delete repository"`, plus the site and risk; the target text comes from the page and is shown quoted. On high-risk cards Enter rejects, so approving takes a deliberate click (or Tab, then Enter). Using the card never closes the page's own menus or popovers, so an approved click inside an open menu still lands.

Approval emails and system notifications never quote page text; they use BrowserPair's own wording with the site and risk only.

## Developer mode

For fewer questions about sensitive steps, choose the account-wide [Developer mode](/developer-mode) on the Permissions page. It affects every connected agent and keeps immutable browser/task safety checks.

## Organization policy

On managed Chrome, an administrator can set `blockedUrlPatterns` for the BrowserPair extension (host patterns that include subdomains). Blocked sites are refused before any input (`blocked_by_browser_policy`) for navigation, links, forms, frames, redirects and tab adoption. The policy can only remove access; neither mode nor an approval can lift it.

## When BrowserPair refuses an action

An action may be refused because the task requires confirmation, the element moved, a Chrome site restriction applies, or a previous effect remains uncertain. Read the current task state before another attempt. Page content cannot grant permission or prove that an action failed.

## Removing a browser

Removing a browser revokes its device credential at once and stops its active tasks. Agent keys scoped **only** to that browser are revoked too, so they can never drift to another browser; keys that also cover other browsers keep working for those. The App lists the affected keys before you confirm, and revocation cannot be undone.

## Sensitive-data disclosure

Protected values are masked by default in Standard mode. An agent requests a specific sensitive category for a task observation. The account-wide **Passwords and secrets** question controls whether it pauses for your approval. There is no current reusable per-agent grant editor. See [Sensitive access](/sensitive-access).

## High-risk effects

Publish, send, delete, payment and other elevated actions follow current account ask-before switches and any immutable task confirmation.

<Note>
  Turning an ask-before switch off removes that optional question; it cannot remove an immutable task confirmation or Chrome restrictions.
</Note>
