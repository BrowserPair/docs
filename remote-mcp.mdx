Use Remote MCP when Claude, Codex, or another MCP-speaking agent should remain the **Brain** while BrowserPair provides scoped access to the user's connected browser.

<CardGroup cols={3}>
  <Card title="Scoped" icon="shield">
    Every tool call stays inside the agent key and task authority.
  </Card>

  <Card title="Durable" icon="arrows-rotate">
    Task identity and effect state survive normal reconnects.
  </Card>

  <Card title="Composable" icon="plug">
    The external Brain can inspect state, delegate bounded Reflex work, request observations, and respond.
  </Card>
</CardGroup>

## Connect

<CardGroup cols={2}>
  <Card title="MCP endpoint" icon="plug">
    `https://mcp.browserpair.com`
  </Card>

  <Card title="Authentication" icon="key">
    `Authorization: Bearer bp_live_…`, or OAuth for AI apps
  </Card>
</CardGroup>

<Note>
  The `bp_live_…` token is an agent credential, not a browser-device credential. The extension never stores the agent key.
</Note>

AI apps such as ChatGPT and Claude can connect without a key: they discover OAuth from the server's `401` response and you choose their limits on a consent screen. See [Connect an AI app](/connect-ai-app).

Every tool declares `readOnlyHint`, `destructiveHint` and `openWorldHint`, and results include a short `guidance` sentence that tells the agent what to do next, for example when a step waits for the user's approval in Chrome or an uncertain effect must be checked before any retry.

## Tool surface

| Tool | Purpose |
| --- | --- |
| `browser_list` | List browser profiles available to the connection, with the name the user gave each one and whether it is online. Pick the browser whose name the user said. |
| `browser_run` | Start one durable bounded browser task. |
| `task_state` | Read current task state and the latest bounded interaction. |
| `task_subgoal` | Delegate a bounded subgoal to BrowserPair Reflex. |
| `task_observe` | Request a fresh browser observation without performing an action. |
| `task_diagnostics` | Read a task tab's console messages or request list (bounded, redacted, no headers or bodies). Needs `diagnostics_read`. |
| Page actions | One tool per step: `task_click`, `task_double_click`, `task_context_click`, `task_fill`, `task_select`, `task_press`, `task_hover`, `task_focus`, `task_scroll`, `task_wait`, `task_drag`, `task_canvas_click`, `task_canvas_drag`, `task_range_click`, `task_upload`, `task_set_viewport`. Each takes a `ref` from the current observation and the `interaction_generation`. To answer a dismissed page confirmation dialog OK, repeat the action with `acceptDialog: true` (always approved by the user in Chrome; see [REST API → Page dialogs](/rest-api#page-dialogs)). |
| Tabs and pages | `task_navigate`, `task_open_tab`, `task_back`, `task_switch_tab`, `task_adopt_tab` (use one of the user's open tabs listed in `open_tabs`), `task_close_tab` (close a tab the task opened). |
| User and effects | `task_user_step` (the user signs in or completes a step themselves), `task_resolve_effect` (decide an uncertain step from a fresh observation). |
| Finish | `task_done` (with `expectedOutcome` criteria the page proves and optional `tabs: keep, result or close`), `task_blocked`, `task_handoff`. |
| `task_cancel` | Cancel the task. |

## Tabs

Each observation lists the task's own tabs (`task_tabs`). By default it also lists the user's open tabs on websites the connection may use (`open_tabs`, with title and address); other tabs are only counted. The user can limit this to the task's own websites, or turn it off, in the App under **Permissions**. An agent may continue in one of the user's tabs with `task_adopt_tab`. That tab stays the user's: BrowserPair never closes it. `task_close_tab` and `task_done tabs: close` close only tabs the task opened.

## Start a task

`browser_run` requires:

<CardGroup cols={3}>
  <Card title="Goal" icon="bullseye">
    What the task should accomplish.
  </Card>

  <Card title="Browser" icon="browser">
    The connected `browser_id` inside the key scope.
  </Card>

  <Card title="Allowed domains" icon="globe">
    One or more explicit task websites.
  </Card>
</CardGroup>

Optional fields are `capabilities`, `confirmations`, and `max_side_effects`.

If capabilities are omitted, BrowserPair uses the ordinary browsing set: `read`, `navigate`, `hover`, `click`, `fill`, and `select`.

<Tip>
  Multiple websites can be authorized at task start. Keep the set as narrow as the workflow allows.
</Tip>

## Recommended external-agent loop

<Steps>
  <Step title="Discover">
    Call `browser_list` and select an online browser inside the key scope.
  </Step>
  <Step title="Create">
    Call `browser_run` with the goal, browser, websites, and required capabilities.
  </Step>
  <Step title="Read state">
    Call `task_state` and use only the current interaction generation.
  </Step>
  <Step title="Choose the next mode">
    Respond directly with `task_respond`, delegate routine work with `task_subgoal`, or request richer context with `task_observe`.
  </Step>
  <Step title="Finish deliberately">
    Report `done`, `blocked`, resolve an uncertain effect, or cancel.
  </Step>
</Steps>

## Delegate to Reflex

`task_subgoal` is useful when the external Brain knows the next bounded objective but does not need to choose every click.

<CardGroup cols={2}>
  <Card title="Bounded work" icon="bolt">
    Provide a subgoal, optional success criteria, and an optional maximum step count.
  </Card>

  <Card title="Skill-aware" icon="wand-magic-sparkles">
    Optionally bind a compatible Skill so Reflex has reusable workflow knowledge.
  </Card>
</CardGroup>

Reflex returns control when confidence is too low, it reaches its bound, or it becomes blocked.

## Request richer context

`task_observe` can request:

- `lite`
- `accessibility`
- `dom`
- `screenshot`
- `combined`

with either `relevant-region` or `full-page` scope.

<Warning>
  Observation depth does not change authority. Account observation policy, domain scope, capabilities, and sensitive-data redaction still apply.
</Warning>

## Respond safely

Current action kinds include `navigate`, `open_tab`, `back`, `adopt_tab`, `click`, `double_click`, `context_click`, `hover`, `fill`, `select`, `focus`, `press`, `scroll`, `wait`, `drag`, `canvas_click`, `range_click`, `done`, `blocked`, and `resolve_effect`. Hover, keys other than Enter, drag and drop, sliders and canvas points each need their own capability (`hover`, `keyboard`, `drag_drop`, `range_interaction`, `canvas_interaction`).

<Warning>
  Never invent a DOM or accessibility ref. Use only refs returned by the current BrowserPair interaction, with the matching interaction generation.
</Warning>

A rejected action says why: `capability_denied` includes `requiredCapability`, `reason` and `grantedCapabilities`, and `resolve_effect` with `definitely_not_executed` is refused (`fresh_observation_required`) until you have called `task_observe` after the uncertain action. See [REST API → When an action is rejected](/rest-api#when-an-action-is-rejected).

## Idempotency

MCP request IDs are mapped to BrowserPair task idempotency keys for `browser_run`. Retrying the same MCP request does not create another task.
